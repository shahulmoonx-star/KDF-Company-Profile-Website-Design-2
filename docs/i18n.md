# Internationalization (English / Arabic)

The site is bilingual: English and Arabic, with Arabic rendered right-to-left. This document records the routing approach and the state of the Arabic translations.

## Routing

Every real page lives under a locale prefix — `/en/...` or `/ar/...` — via Next.js App Router's `src/app/[locale]/` convention. There is no unprefixed route: `src/proxy.ts` (this Next.js version's renamed `middleware` — see the version-history note in `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`) redirects any request with no locale segment to one, chosen by:

1. A `kdf_locale` cookie, if the visitor has one (set on their first visit, and rewritten whenever they use the language switcher).
2. Otherwise, the browser's `Accept-Language` header.
3. Otherwise, English (`defaultLocale` in `src/lib/i18n/config.ts`).

This is a proper i18n routing setup rather than a client-side toggle: each language gets shareable, indexable URLs, and `generateMetadata()` in `src/app/[locale]/layout.tsx` emits `alternates.languages` (hreflang) for both. An invalid locale segment (anything not in `locales`) 404s via `notFound()`.

## Adding a third locale

Add it to the `locales` tuple in `src/lib/i18n/config.ts` (and to `rtlLocales` there if it reads right-to-left). Everything else — the proxy's redirect matching, `generateStaticParams()`, the language switcher, and every content accessor — derives from that list; no other file needs to change to add the *routing*. Content still needs the new language's translations added to each accessor.

## Content vs. chrome

Two different mechanisms carry text, deliberately:

- **Content** (navigation labels, site name, page copy) goes through the same typed accessors as everything else in `src/lib/content/`, now taking a `Locale` parameter — e.g. `getMainNavigation(locale)`. Internally each accessor keeps a locale-keyed source object (`Record<Locale, string>` per field) and projects it down to the plain, already-localized shape (`NavItem`, `SiteSettings`) that components consume — matching how the real API will behave once it exists (it takes a `locale` param and returns already-localized strings; see `backend-integration-plan.md`).
- **UI chrome** (aria-labels like "Open menu", the language switcher's own labels) is not CMS content — it will never come from the API — so it lives as a small static dictionary in `src/lib/i18n/ui-strings.ts` instead.

## RTL

`src/app/[locale]/layout.tsx` sets `dir="rtl"` on `<html>` for Arabic (`directionFor()` in `src/lib/i18n/config.ts`). Everything laid out with `flex`/`grid` mirrors automatically — this is native CSS behavior under `dir="rtl"`, not something coded per component. The navbar's logo, for instance, needs zero RTL-specific code: it moves from the left edge to the right edge purely because the browser reverses the flex row's inline direction.

**The loading screen is a deliberate exception.** It is not RTL-aware and always renders its caption text in English, regardless of site locale. This was a scope decision, not an oversight: the loader is fragile (see the standing note on it), it appears before a visitor has necessarily engaged with the language switcher, and its runtime-measurement design (see `src/components/LoadingScreen.tsx`) already re-targets correctly to wherever the mirrored navbar logo actually lands — verified pixel-exact in both directions. Only its caption copy stays English. Revisit if the client asks for it.

## Translation status

The Arabic strings throughout `src/lib/content/` are a first-pass professional translation, not yet reviewed by KDF. Two things worth flagging before launch:

- The Arabic company name (`الشركة الكويتية لسوائل الحفر والخدمات النفطية`) is taken directly from the wordmark on `public/images/logo.png`, not translated fresh, so it stays consistent with the printed brand mark.
- Where a nav item looked like a branded product-line name rather than a generic description (`Treat Chemistry`, `Protect Chemistry`, `Assure Chemistry` under Production Chemistry), the brand word was kept in Latin script per common Gulf bilingual-corporate convention (e.g. "كيمياء Treat"), rather than translated outright — confirm with KDF whether these are in fact registered program names.
- "Cementing" is rendered as "الإسمنت" (cement), standard Arabic technical usage, rather than a literal word-for-word translation of "cementing."
- The homepage copy (`src/lib/content/home.ts`) is written to be read rather than transliterated, so it is not a sentence-for-sentence mirror of the English. Its oilfield vocabulary is the part most worth a specialist's eye: shale as "الصخور الطفلية" (not "الصخر الزيتي", which is oil shale — a different substance), lost circulation as "فقد الدوران", roller mills as "مطاحن أسطوانية". Confirm these with KDF's own Arabic technical material if any exists.
- Figures use Western digits and comma grouping in both languages (`450`, `28,800,000`), matching Gulf corporate publishing convention and keeping the two versions of a number identical.

Treat every Arabic string in this codebase as a placeholder pending that review, the same way `website-content-source.md` flags inconsistencies in the English source material for confirmation.
